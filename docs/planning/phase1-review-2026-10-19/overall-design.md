## 3. 复用架构与取舍

| 方案 | 收益与代价 | 选择 |
| --- | --- | --- |
| A：受控复用旧后端整域及 Worker，新业务独立部署，共享公共表 | 保留 DI、DTO/Guard、RLS、文件/任务/工具/产物契约；承担 Hub/Study/注册适配和共享兼容验证 | **推荐待审**，最符合 C04/C05/C08 |
| B：新前端直接调用旧系统整套运行后端 | 初期接入快，但新能力发布、模型配置、任务和故障与旧运行服务强耦合 | 不作为独立交付主方案；只可在合成环境作接口探针 |
| C：逐 Service 抽取并重造依赖 | 单个纯函数适用；复杂域会丢 Guard、审计、配额、任务与存储契约 | 不作为主方案，纯策略/确定性算子例外 |

推荐部署组成：

- **旧业务部署：**原域名/前后端继续服务；只接受必要租户边界修补和兼容变更，不替换旧 UI 或旧研究配置。
- **ResearchHub 部署：**hub.pengxc.com、现有前端与独立 API/Agent 运行配置、受控复用的 Parser/Embedding/方法 Worker；沿用既有独立发布边界。后端具体端口/资源容量在部署设计锁定，不挤占现有端口。
- **共用控制面：**优先复用现有平台超管租户管理入口，统一管理租户、配额、功能开关与主题；这是共用能力，不要求重写一个微服务或给两个项目各造一套控制台。
- **共用持久层：**同一 PG 实例/库/现有公共表；业务作用域按租户/成员限制；对象存储至少有租户命名空间和鉴权下载，不把公网 URL 当授权。
- **故障边界：**独立应用发布不等于共享 DB、算力或存储没有共同故障风险；需容量预算和迁移窗口。本文不承诺物理故障隔离或未经配置的灾备 SLA。

知识 UI 复用包括编辑器、原件/版本/审核/回收站、对话框、API 错误和上传契约，局部映射旧 CSS/Tailwind Token；不搬旧 Shell 覆盖冻结导航。新旧锁文件/运行镜像版本分别固定，不顺便升级全仓依赖。

## 4. 共享数据库与模型设计

### 4.1 身份与租户

保留 `Tenant`、`Account`、成员/权限、知识、会话、数据、方案/表单、产物与审计等现有公共物理表。新旧甲方数据写入不同 tenantId；**不新建一套 researchhub_account、researchhub_knowledge 或患者平行表**。ResearchHub 特有的 Hub、意图 Project、Source/Canonical、邀请等对象可作兼容增量，不将“共享表”误解为禁止新增实体。

第一期 Account 仍属于单租户，保留 `(tenantId, username)` 唯一约束；不按姓名/同名邮箱自动合并新旧账户，不提前建设全局跨租户 SSO。机构、Hub、课题组和租户不互相等同：跨机构合作可在灵枢心域同一租户内，通过 Hub/Study/中心成员关系表达。

### 4.2 Project / Study / Protocol

- 新意图 Project 持有 Question/PICO，与执行 Study 区分。
- 旧 `ResearchProject` 已挂接执行数据/FK，继续保留其数据库身份；新 Study 显式映射该执行聚合，并关联 Hub 和意图 Project。首期可采用清晰的 1:1 映射，不全表改名，不宣称已有任意多 Study 能力。
- Protocol、CRF、量表、数据快照及产物版本不混为同一版本。sourceId/版本/hash、操作人和来源链贯穿。
- 元数据/Schema-only 核查可以先做；不需要患者数据才能设计。真实配置读取必须限定 tenant/group/project/版本，并只导出专业配置和必要元数据。

### 4.3 唯一迁移与兼容发布

推荐首期沿用 `app/server/prisma/migrations` 作为**唯一共享库迁移入口**，由主集成统一串行管理；ResearchHub 可生成兼容客户端，但不能独立维护第二套自动执行迁移历史。路径归属为待评审工程决策，不在本轮搬代码或执行迁移。

增量采用 expand→验证→逐应用启用，优先新增可空字段/扩展表及兼容索引，禁止首期直接删旧列、改旧含义、全表重命名或用 db push 覆盖运行库。约束/默认值/枚举也需旧客户端回归，不是只有 DDL 成功。迁移前在合成克隆环境重放并执行新旧版本读写与恢复；生产前确认备份可恢复、锁表/资源影响、发布顺序。应用回滚不依赖删除新表/数据。

旧通用 seed 会更新已有账号和关联，不能作为新项目初始化脚本直接运行；全量 rls.sql 会影响共享public表，须纳入兼容发布。`tenantId=null` 的官方Skill/知识/量表/模板是明确共享资源，修改会影响两个产品；优先追加不可变版本，不把全局只读共享误当租户私有。

## 5. 注册、成员与权限

### 5.1 公开注册闭环

建议服务端配置将可信入口 hub.pengxc.com 绑定新租户；请求体、URL、任意 Host/转发头不能自行选择其他租户。验证渠道建议使用已配置的邮件服务，具体供应商/费用由 Q04 收口；不把邮箱验证等同 L2/L3。

注册→验证码/凭证校验→创建基础 Account→登录→无研究成员的个人空态。复用哈希/会话撤销/唯一性/审计，不直接调用会自动加入默认课题组的旧管理员建账号流程。不得自动赋予 tenant_admin、PI、默认 Study 或全租户知识权限。

找回密码复用 authVersion 失效机制，增加一次性、过期、不可重放凭证、统一响应和限流；不是开放管理员 reset-password。邀请绑定租户、Study、目标身份、角色/中心范围、签发人、有效期、撤销与一次性接受；接受事务失败不得留下部分成员权限，重复接受结果幂等。

### 5.2 角色与控制面

| 身份 | 允许范围 | 不能据此获得 |
| --- | --- | --- |
| 平台超管 | 经审计的跨租户配置与管理 | 面向普通用户的跨租户私有数据入口 |
| 租户管理员 | 本租户账户/配置管理 | 自动成为所有 Study 的 PI 或 Hub负责人 |
| Hub负责人 | 已确认的本 Hub 内容与研究数据治理，可科研和采集 | 其他 Hub/租户数据；不能直接借 platform_admin 绕过 |
| PI | 指定 Study 的方案/审阅/锁解锁等业务动作 | 其他 Study 的 PI 权限 |
| 采集人员 | 授权 Study/中心采集、更正，锁定后拒绝编辑 | 锁解锁或其他中心/Study 数据 |
| 基础注册用户 | 公开内容、本人资料及获授权资源 | 任何未邀请的私有 Study/知识库/AI上下文 |

同一人可兼任业务角色；不能把三业务角色强行映射为旧三个技术 role。服务端 Guard + 资源策略 + 受限 DB 角色/RLS 共同实施，平台控制面的高权限路径另行审计。当前代码存在 elevated 和 ScaleItem 父关系例外，不能写“已有 RLS 所以全链安全”。

## 6. 实施前共享表/后台任务验证与允许改动

**先完成G0风险验证和必要修补，再以G1通过作为启用共享正式运行环境新租户业务任务的门槛。** G0/G1可在隔离合成环境预置任务/API探针；它不替代后续公开注册或完整知识UI验收。在合成环境构造旧租户 A、新租户 B、两个应用实例及相同种类队列，检查：

1. 任务扫描/恢复/领取/执行/取消/失败重试/超时回收均只处理本部署获准租户，不能仅在 API 入口过滤。
2. 任务领取有原子状态比较；必要时补 workerOwner/lease/heartbeat，验证重启和并发不重复执行、不抢回另一实例合法任务。是否增加字段由实际测试决定，不机械要求另建队列系统。
3. 已发现至少四类全局扫描：知识导入、知识对话、原始处理、科研Agent运行/阶段重试；提醒、情报、导出和方法任务也逐类登记，不因有任务表就断言存在同样Worker。数据选择后使用记录租户的完整受权上下文；后台重核租户/账号/成员有效状态。
4. 登录/JWT、搜索/向量检索、下载/导出、AI上下文与运行目录、缓存/上传/审计都以同样的租户/Study 边界验证。

知识导入目前只有进程内active集合，必须验证跨实例原子领取；科研陈旧运行恢复需重核时间/归属，避免把对方仍活跃任务判败。分块上传清理器也需独立部署临时目录，不能只隔离PG表而让本地文件互删。静态证据与路径见[复核记录](source-evidence.md)。

**必要旧后台改动白名单：**部署允许租户绑定；认证/队列作用域校验；恢复与任务租约；与其直接关联的 DB 兼容迁移、审计和测试。新增 ResearchHub 业务在新受控代码基线实现，不借此重构旧业务或开启退役检测。

发布顺序建议：冻结旧基线→合成双实例验证→旧后台最小修补回归→受控发布验证→才启用新租户业务写入/任务。不能先往共享队列写新任务，再补旧 worker 过滤。失败时停止新任务，不破坏原租户，按已验证版本回退。
