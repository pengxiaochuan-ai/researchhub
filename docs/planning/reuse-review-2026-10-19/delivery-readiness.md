## 2. 开发前必须拍板

| 决策 | 推荐起点 | 不确认的影响 |
| --- | --- | --- |
| 首期验收性质 | 具备真实后端的单 Hub 受控试运行，不是只交静态 Demo，也不默认承诺完整商业 SaaS | 无法冻结范围和验收数据 |
| 代码组织 | 现有 researchhub 前端 + 旧 app/server 整域后端与配套 workers 的受控开发基线 | 零散复制 Service 会反复补 Prisma、Guard、任务、存储依赖 |
| 数据库 | 优先 PostgreSQL/pgvector，沿用旧 schema/迁移/RLS；Hub 等作为增量，不为历史 MySQL 建议重写 | 强行换库会扩大改造和安全验证 |
| 旧系统运行方式 | 保持原系统独立，先在隔离开发/验收环境复现；是否最终合并部署另确认 | 两套未经适配的服务共写旧生产库有破坏风险 |
| 对象语义 | 旧 ResearchProject 保留执行数据/FK；新增独立意图 Project 与 Study 映射，不全表重命名 | 会把研究意图、执行、权限和数据血缘混为一体 |
| 业务角色 | 已确认 Hub负责人 / PI / 采集；Hub负责人不等同于旧平台/租户技术超管 | 简单借超管标志会超过 Hub 授权边界 |
| 身份路径 | 明确公开注册/找回/邀请及 L2/L3 是否均为本次硬验收；人工审核可简化 UI，不可伪造资格或越权 | 旧租户账号不能自动变跨机构统一账号 |
| 首个研究 | 提供真实项目 ID、方案/访视/CRF版本和实际人员，由专业方确认 | 演示 seed 和注册摘要不能替代真实配置 |

以上是架构建议，需确认后形成 Accepted ADR 再实施；本轮没有修改运行代码或数据库。
