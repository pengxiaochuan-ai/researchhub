## 本地关注投影与用户文案

仅依据原summary已经明确返回的字段派生布尔关注标记和简短原因，不持久化、不改变数据或业务资格。

| 原返回事实 | 可读原因 | 规则边界 |
| --- | --- | --- |
| `unavailable`明确返回 | “暂不可核对”，保留原原因 | 不把来源或访问问题冒称临床数据异常；不可勾选资格仍由原规则判定 |
| `required===true`且尚无已提交response | “必采尚未提交” | 不自动分配、提交或补答案；豁免/不适用的对应关系须按下方未决项核定 |
| 已返回score的`processingStatus==='incomplete_data'` | “资料待补齐” | 原评分详情、缺失及不适用记录照常显示，不补0 |
| 已返回score的`processingStatus==='awaiting_policy'` | “待规则确认” | 不生成总分或默认通过 |
| 已返回score的`processingStatus==='review_required'` | “评分依据待复核” | 不新增临床判断或阈值 |
| 已返回score的`scoreComplete===false` | “评分尚未完成” | 字段缺省、null、未知值不等同于false |
| 已返回score的有效`missingRequired>0`或非空`unresolvedItems` | “有待核条目”，原详情保留 | 只认明确类型/值，不把未返回字段补成0或空数组 |

多个明确原因可并列，避免重复说明同一状态。`total=0`是有效数值，不因真假值判断标成缺失；不以total、classification、diagnosis或是否达到阈值决定排序。未知/未返回/N-A不贴“正常”标签，也不静默改成0；只有已知明确关注信号才进入“需关注”，其余保持原状态表述，不称正常组。

独立审核限制单独显示“待其他人员审阅”，属于责任/权限状态，不单凭它标记为数据异常；如同时存在明确资料问题，可分别显示原因。审核人仍须打开并核对每份原题、答案及固定修订，再自行选择；关注排序不表示可批准。

建议固定文案：“全部”“需关注”；无明确关注项时为“本清单暂无明确关注标记，仍需逐份核对。”；筛选无结果不替代无表单空态。页面不展示hash、接口、测试、开发进度或本轮预算说明。

## 选择与确认的同步失效

筛选change立即清除未提交选择并关闭本次确认；不得仅隐藏已勾选行而让其继续进入处理范围。默认选中集合始终为空，筛回“全部”不恢复旧选择。筛选不调用load/start/resume、不中断或重排已创建批次，也不新增storage、dirty或beforeunload。

为当前视图保留同步的来源绑定，至少覆盖：当前tenant、actor、authVersion（0合法）、Study、visitId、当前URL、summaryHash、原行身份/修订/动作/资格，以及实际返回的score关注投影。score不存在与返回null须区分；相关flags、missingRequired、unresolvedItems改变，即使summaryHash不变也必须使旧选择与确认失效。可在内存对实际score作稳定快照；不增加后台hash或把正文写入标记。

失效必须同时发生在以下三处，不能只依赖effect清理：

1. 本次render先核当前来源绑定，不让旧选择或旧确认呈现为可用；effect仅做后续状态归整。
2. 打开确认时绑定当下filter、URL、来源投影及原固定refs，并再次用原`reviewItemEligible/visitReviewSelection`核范围。
3. 确认回调紧邻`workflow.start`前同步重查最新render来源与当前URL；已捕获的旧dialog回调在筛选、身份/version、Study/visit/URL、score flags或来源变化后不得调用start。关闭旧确认按原ConfirmDialog恢复焦点，旧触发元素已消失时回面板fallback。

保留原确认框、原native eligibility、逐项CAS及独立审核。提交内容仍是原显式assignment IDs/version/ref；本地关注字段不进入mutation、不能扩大canReview/canLock。批次恢复、unknown GET、原键证明、部分成功及明确继续逻辑完全不动。
