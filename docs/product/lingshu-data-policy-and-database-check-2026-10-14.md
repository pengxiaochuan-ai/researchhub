# 三角色、数据更正与旧库核查确认

日期：2026-10-14。状态：角色、数据更正、PI控制及迁移方向由用户确认；旧库文件结果为只读核查事实。覆盖此前“Hub负责人仅公开内容”“采集提交后须退回方可修改”等建议。

## 1. 首期只设三类业务角色

| 角色 | 权限 |
| --- | --- |
| Hub负责人 | 默认查看和管理本Hub全部内容，包括课题/Study和研究数据、领域内容、学术活动；可自行开展课题研究和数据采集，具备本Hub内PI及采集能力 |
| PI | 管理其Study方案/成员/数据，审阅数据、锁定/解锁、研究产出与共享；操作留痕 |
| 采集人员 | 在被授权研究/中心范围采集、提交、更正数据、回复疑问；不得自行解锁 |

Hub负责人不是仅做内容运营的角色。权限应在服务端按hubId及其所辖研究落实，不能只是前端显示管理员按钮；不自动获得其他Hub权限。机构/平台控制面的技术身份不作为首期新增业务角色对用户配置。

质控、评价、统计、内容发布首先作为任务与权限动作，由上述三角色承担；不要求新增用户角色。一人可兼任。具体研究未来要求盲态等限制时，由方案明确处理，不默认宣称当前已有完整揭盲能力。

## 2. 采集提交后的更正

用户确认：采集人员提交后可以修改，必须记录修改日志、前后内容及历史版本。

实现目标：原提交生成不可覆盖revision；后续每次更正生成新revision，记录操作者、时间、修改原因、字段旧值/新值及所对应Protocol/CRF版本。可查看完整历史、版本对比和指定版本内容，不能只保留当前值。

PI审阅的结论绑定具体数据revision；更正后新版本进入待审阅，旧审阅记录保留，不把已审阅标记自动沿用到更正后的内容。

PI负责锁定和解锁，动作记录对象范围、理由、操作者和时间。锁定后普通编辑被拒绝，须PI解锁后更正；Hub负责人使用其PI能力操作时同样留下记录。并发保存需要expectedRevision检测，冲突不覆盖。数据、历史版本与修改审计同事务写入。

## 3. 原研究迁移方向

开发完成后，把原课题及其数据迁入当前系统，作为灵枢心域Hub下的一项课题/Study。不是仅复用代码或只关联公开摘要。

准备迁移清单：源tenant/studyGroup/researchProject → 目标Hub/Project/Study，账号 → 统一个人账号与三角色，Protocol/访视/表单/量表版本与适用关系，受试者/访视/响应、文件与来源、疑问/任务/产物和审计。保留源ID映射、版本、来源及可核对的记录数，不按名称自动合并账号。

数据库与文件存储是两部分：附件/原始文件若在MinIO/OSS，仅有数据库引用不等于已迁移文件。先配置和合成样例验证，再做授权迁移预演、对账及切换，原系统不在本轮停用或改库。
