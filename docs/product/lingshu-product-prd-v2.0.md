## 1. 产品层级与首期目标

| 层级 | 产品职责 | 首期实现 |
| --- | --- | --- |
| 岐研 Platform | 统一账号、科研身份、多机构关系、Hub 注册与治理、通用科研引擎、资产与 AI 基础能力 | 实现可扩展底座，首期开放灵枢心域 |
| Organization 机构 | 机构身份、资源、站点和研究治理边界 | 支持用户关联多机构、同一研究多中心协作 |
| Research Hub | 围绕领域组织公开证据、机会、研究者与经授权的研究/资产 | 灵枢心域：针灸防治情志病 |
| Research Project 研究课题 | 研究意图、核心问题、PICO、来源与科研目标 | 个人草稿到正式研究的前置对象 |
| Study 研究 | 方案、成员、中心、执行、质量、分析、产出 | 团队自治；权限不由 Hub 自动继承 |
| Research Asset | 有来源、版本、权属、发布范围与复用记录的价值对象 | 经人工确认和治理后进入 Hub |

Hub 是领域空间，不是机构租户，也不是 Study 的数据所有者。机构可共建多个 Hub；一个 Hub 可连接多机构。用户可参与多个机构、Hub 和 Study，不因切换机构而创建重复账号。

首期成功目标：四类用户均能从明确入口完成真实账号与身份流程；王教授可查看领域变化、形成课题、组织研究；受邀成员完成限定范围内任务；成果经授权返回灵枢心域并可追溯复用。首期不要求上线其他领域 Hub，但所有接口和存储禁止把唯一 Hub 写死为全平台规则。

## 2. 建设方式与选择理由

1. 单独做灵枢心域应用：最快呈现，但账号、资产、机构与科研流程容易重复建设，无法满足多 Hub 平台定位。
2. 先完整建设通用 SaaS 再建设 Hub：复用度高，但会把首期消耗在计费、租户控制台和平台运营上。
3. **采用通用底座 + 单 Hub 先行。** 账号与权限、数据分层、Hub 配置通用化，灵枢心域提供首期内容与真实研究验收。其他 Hub 暂不开放自助创建，不复制另一套前端或数据库。

## 3. 账号、身份、角色与权限

### 3.1 四级科研身份

| 状态 | 含义 | 产品能力与升级时机 |
| --- | --- | --- |
| 访客 | 未登录，无平台账号 | 浏览经批准的公开内容；不产生成员身份 |
| L0 | 已注册普通平台用户 | 浏览公开内容；引导建立科研资料 |
| L1 | 已建立个人科研身份 | 我的科研、关注 Hub、收藏证据、课题草稿、基础 Copilot |
| L2 | 已认证科研人员 | 按策略创建 Study、接受正式研究角色、贡献与提交资产 |
| L3 | 已认证机构科研关系 | 在该机构授权范围使用机构资源、参与正式机构研究 |

L3 必须保存到具体机构关系，不能只保存一个全局等级。用户在机构 A 已认证，不代表在机构 B 已认证。身份界面可显示最高完成等级，但判断资格必须读取有效认证记录、机构、有效期与撤销状态。认证状态采用 `NOT_SUBMITTED / PENDING / VERIFIED / REJECTED / EXPIRED / REVOKED`；失败提供原因与重新提交入口。

科研身份决定资格，角色决定责任，Scope 与授权决定具体数据可见性。注册页不让用户选择“我是管理员”来获取权限。四类路径可选作进入目的；同一用户可以同时承担多个角色。

### 3.2 四种上下文角色

| 上下文 | 建议角色 | 授权边界 |
| --- | --- | --- |
| Platform | 用户、认证审核员、平台治理员 | 账号/认证/Hub治理各自授权；无默认研究原始数据访问权 |
| Organization | 成员、机构审核员、机构管理员 | 仅本机构资格、资源与治理职责 |
| Hub | Hub负责人 | 本Hub领域、活动、课题与全部研究数据管理，含研究和采集能力；关注/贡献作为参与状态或动作 |
| Study | PI、采集人员 | PI负责研究管理、审阅/锁定/解锁；采集负责录入/提交/更正；Hub负责人具有本Hub内上述能力 |

旧资料中把 Hub 参与也命名 L0–L3，容易与科研身份冲突。V2 Hub 一律使用角色名和成员状态，不复用 L0–L3。

### 3.3 关键权限规则

- 关注 Hub 不等于加入 Study；加入 Study 不等于获得全部数据。
- Hub负责人默认管理本Hub内全部课题/Study及数据，并可开展研究和采集；普通关注/贡献者不继承这些权限，其他Hub权限不自动获得。
- L2 可以创建科研设计草稿和满足策略的非机构研究；涉及正式临床执行、机构资源或患者数据时，要求对应机构 L3、有效成员授权及必要治理结果。
- PI 获得该 Study 的管理职责，但导出、共享、原始身份数据和 AI 使用仍受资源政策约束，不默认全部放开。
- 推荐授权判定：账号有效 + 资源上下文有效 + 必要资格有效 + 有效成员角色 + Scope 覆盖 + 动作授权 + 资源策略。任何环节拒绝即拒绝；公开资源走明确的公开读取策略。
- 前端隐藏/禁用按钮只解释资格；后端负责所有读写、搜索、下载、AI 检索和导出的实际授权。URL 参数不是权限凭据。

## 4. 数据与 SaaS 边界

### 4.1 领域对象关系

```text
统一账号 → 科研身份 → 多机构认证关系
                 ↘ Hub 关注/贡献/治理关系
                 ↘ Study 成员 → Role + Site/Scope + Permission

机构 ← 多对多共建 → Hub ← 领域关联 → Study
                                      ↑
Evidence → Opportunity → Project（内含核心 Question/PICO）
                                      ↓
Protocol 版本 → 执行/数据质量 → Analysis → Output/Artifact
                                      ↓
                           人工治理 → Asset → Hub 复用
```

Project 可有多个 Study；首期界面可从一项 Study 开始，但数据库不把 Project、Study、Protocol 合并成同一个对象。Study 可独立发起，UI 先补齐课题意图/问题，再进入研究设计；不要求先关注 Hub。首期 Study 选择一个主 Hub；数据模型预留多 Hub 关联，其他关联只在授权后开放研究摘要，不复制受控数据。

### 4.2 建议逻辑对象与最小字段

| 对象 | 最小字段/约束 |
| --- | --- |
| account / researcher_profile | userId、状态；profileId、研究方向、个人科研经历 |
| identity_verification | userId、类型、机构ID（机构认证时必填）、状态、有效期、审核依据 |
| organization_membership | userId、organizationId、角色、状态；支持多机构 |
| research_hub / hub_scope | hubId、slug、名称、领域边界、品牌配置、状态、scopeVersion |
| hub_organization | hubId、organizationId、共建职责、有效状态；不意味着共享全部资产 |
| hub_user_membership | hubId、userId、角色、关注/成员状态、授权人 |
| hub_proposal / proposal_review | 发起人、范围快照、相似性结果、修订版本、审核意见 |
| research_project / research_question | projectId、owner、hub关联；questionId、projectId、PICO、证据来源 |
| research_study / study_hub_link | studyId、projectId（独立发起完成课题信息后关联）、主机构、状态；Hub关联与摘要可见范围 |
| protocol_version | protocolId、studyId、不可覆盖版本、审查状态 |
| study_invitation | tokenHash、目标账号/邮箱、studyId、拟授角色/Scope、过期时间、状态；不存可复用明文令牌 |
| study_membership / study_site / resource_grant | 用户、Study、角色、中心、操作范围、授权人、有效期 |
| research_asset / asset_version / asset_share_request | 保留现有字典的来源、权属、版本、敏感度；增加明确共享申请与审批对象 |
| audit_event | actor、上下文、资源、动作、结果、时间、策略版本；正式审计由服务端生成 |

这是逻辑增量，不是已审批的物理表迁移。原 Excel V1.1 字段字典继续管理 Source/Canonical/Hub/Research Work/Asset，后续建立 V2 增量字典再建表。现有 `hub_entity_membership` 表示领域实体归属，不能拿来存用户成员；现实世界 `researcher` 实体不能与已注册 `account` 强制一对一，必须经本人认领或人工确认关联。

### 4.3 数据分层与隔离

沿用现有 Source → Canonical → Hub → Research Work → Asset → Intelligence 分层。公开外部事实可在多个 Hub 被引用；机构/团队/Study 的私有资源需独立授权，不能因为领域归属就复制或公开。

首期建议一个 SaaS 实例支持多机构。SaaS 部署租户的具体模型（一个机构还是机构联盟）单独决策，不把 `tenantId = organizationId = hubId`。若采用多租户，租户为运营隔离边界；跨机构共建仍通过显式关系与共享授权实现。所有私有存储、搜索缓存、对象下载和后台任务须绑定服务端解析的资源上下文，禁止只靠客户端传来的 tenant/org/hub ID 过滤。

Dataset 行数据放在受控研究数据存储；元数据与版本记录放在资产层。AI 检索先做权限过滤；派生结果继承输入限制。对不明确的敏感度、授权或去标识化状态采用限制访问策略，不直接进入公开 Hub。

## 5. 核心业务需求

| 编号 | 需求与行为 | 优先级 | 验收 |
| --- | --- | --- | --- |
| FR-01 | 统一注册、登录、找回密码，登录后恢复原进入目的 | 首期必须 | 从邀请、Hub、Study进入，登录后返回相应上下文；不固定返回王教授工作台 |
| FR-02 | 资料建立与 L2/L3 按需认证 | 首期必须 | 未认证保留草稿；升级后继续原任务；机构认证只对对应机构有效 |
| FR-03 | 我的科研展示我的 Study、关注的 Hub、Brief、待判断/待办 | 首期必须 | 不同用户看到自身内容；没有研究时使用明确空态 |
| FR-04 | 灵枢心域公开门户与 Hub 内容、关注/贡献入口 | 首期必须 | 公开与受限内容分离；关注可取消，不自动加入研究 |
| FR-05 | 灵枢心域范围初始化、共建职责治理；通用Hub Proposal三步申请后续开放 | 首期固定Hub治理，通用创建后续 | H02–H04保留三步；最终提交申请，不直接宣告创建成功 |
| FR-06 | 研究机会形成 Project，保留 Question/PICO 与来源 | 首期必须 | Evidence→Opportunity→Project可回溯；不存在对象不得替换为固定示例 |
| FR-07 | PI创建 Study、设计版本与必要机构治理 | 首期必须 | L1可存课题草稿；正式研究不绕过资格与审批；Hub Steward不能替代机构审批 |
| FR-08 | Study邀请、接受、角色与中心Scope | 首期必须 | 过期/撤销/错账号/重复接受可解释；权限缺失不自动提升身份 |
| FR-09 | 自建EDC：受试者、访视/CRF采集、数据疑问、审阅签署、锁定、导出与审计；约定分析 | 首期必须，用户已确认无EDC | 成员只能访问被授权中心与资源；真实记录持久化且可审计 |
| FR-10 | Output→候选Asset→发布治理→Hub展示→复用 | 首期必须 | PI或指定Publisher授权共享；保留作者、Study、版本与派生链；敏感数据不默认公开 |
| FR-11 | Evidence-grounded Copilot | 首期约定能力 | 有来源、解释、不确定性与人类确认；服务失败不展示伪造AI结果 |
| FR-12 | 多机构多Hub适配 | 底座必须，运营后续 | 使用两个Hub和两个机构测试夹具验证不串数据；只公开上线一个Hub |

### 5.1 Hub 创建状态

建议：`DRAFT → SUBMITTED → UNDER_REVIEW → APPROVED/CHANGES_REQUESTED/REJECTED`；批准后创建 `ACTIVE Hub`，以后可归档。重新提交保留申请版本及审核历史。相似性检查是建议，不是审批；AI不可批准或自动合并 Hub。

本版替代旧 H00 PRD 的“V1无审批、直接创建”目标规则。王教授现有 Hub 可经平台治理人工初始化，记录决策、范围与发起人，不必在首期重复申请。普通用户先提交共建意向；多 Hub 自助创建后续开放，避免首期被平台运营功能拖慢。

正式 Hub 是否一律要求 L3，采用“公共正式/使用机构资源的 Hub 要求有效机构认证；其他申请至少 L2”的建议政策。图片 Hub 发起者按 L3 路径展示，首期灵枢心域执行该严格路径。

### 5.2 Study 与治理状态

Study：`DRAFT → DESIGNING → READY_FOR_REVIEW → APPROVED/CHANGES_REQUESTED → ACTIVE → COMPLETED → ARCHIVED`。非机构设计研究可按策略免审批，但必须显式记录策略依据；机构正式研究不得用“免审批”入口绕过。伦理材料记录系统管理状态，不冒充伦理批准。

创建研究草稿时记录创建者为草稿 PI；草稿阶段只能协作设计。满足资格、研究治理和成员授权后才允许执行与数据访问。创建完成后持有 Study PI 角色不改变平台等级，也不授予其他 Study 权限。

Asset：`DRAFT → CANDIDATE → REVIEW_PENDING → APPROVED/PUBLISHED 或 CHANGES_REQUESTED/REJECTED → WITHDRAWN`。发布范围明确为个人/Study/指定机构/Hub授权成员/公开；进入 Hub 的摘要与资产正文分开授权。Steward负责 Hub内容纳入，不替代资产权利人授权。

## 6. 灵枢心域第一期范围

必须完成：领域范围确认；首期来源采集与追溯；账号和资格；王教授及共建机构关系；四类路径；一条真实课题与方案/协作/数据/产出/资产复用闭环；角色范围与审计；现有页面服务接入。

王教授已明确抑郁、失眠、认知障碍等为重点方向；具体疾病/人群、干预、研究类型、排除条件与术语映射仍需确认。焦虑等宽检索词先保留为候选检索范围，不据此自动新增临床采集模板。

暂缓：SaaS计费、订阅套餐、租户自助开通、其他领域运营、全自动Hub创建/合并、复杂推荐排名、全套通用EDC规则编辑器、未经约定的统计模型。合同新增范围需另行确认，原始附件不改写。

## 8. 总体验收与需评审的政策

验收至少包括：四条用户路径；跨Hub/跨机构/跨Study拒绝越权；L3机构有效期；邀请过期/撤销与幂等；方案版本与治理；共享范围与派生权限；来源变更、去重和指标复算；AI引用与服务失败；1920×1200、1440×900和移动端关键入口。

需后续产品评审：具体认证审核材料/负责方/有效期；正式研究的机构治理条件；SaaS租户运营边界；资产发布责任人；王教授确认的范围与首批研究。上述政策在完成评审前不得以假成功或隐式授权落地。

## 10. 专业材料修订R1：领域优先与数据采集

### 10.1 与关系说明的对照

总体定位一致。首期必须先呈现灵枢心域专业体验：P002为主要公开入口，固定首个Hub配置；H02–H04通用新Hub创建对普通用户暂不开放。现有页面用于领域证据、研究设计/执行与资产，不为了未来平台运营牺牲当前价值。保留多机构/多Hub模型及隔离测试夹具，不先建设多Hub运营门户或统一套餐系统。

“正式Hub申请治理”是未来目标规则，首期仅需要灵枢心域初始化与授权共建；王教授身份、Study归属和机构责任不靠系统默认管理员生成。未确认的认证材料/审批责任人继续作为待评审政策。

### 10.2 范围采用三层

| 层 | 已有依据 | 产品规则 |
| --- | --- | --- |
| 临床研究重点 | 王教授说明抑郁、失眠、认知障碍 | 作为首期领域主入口与筛选优先项；每个Study有独立诊断/人群/纳排 |
| 文献候选范围 | 提供的SU检索式、中英文文献表 | 广泛检索后分类、筛选、人工确认；不等同于统一临床研究标准 |
| 学术共同体主题 | PPT中的中医心理学、多学科讲座、线下交流 | 活动与资料栏目承接；不因讲座主题扩大临床数据采集范围 |

保留教授原中文检索式全文与版本（见本文附录），建立疾病/症状/中医病名/干预分别的术语记录及专家映射。认知方向在中文式中缺少明确关键词，待确认后补充；英文式由数据库适配并结合教授后续资料定稿。机器翻译不是范围确认。知识库可以保留经授权的机制/动物与综述资料，临床注册和临床证据统计需单独筛选，不能一刀切删除全部非临床知识。

### 10.3 首批文献底座

现有合并表：英文5,160条、中文10,536条，合计15,696条记录，非唯一论文/研究数。来源分表不追加计数。两表均需二次质量检查：DOI/URL/摘要缺失、候选重复、来源差异、文献类型与领域归属。中文合并表有92组规范化DOI重复候选，不能直接删除或宣称已经完成科学去重。

新增文献导入批次、文件哈希、sheet/row定位、字段映射、导入错误、候选去重/人工决策和重放记录；保存原表与每条来源，规范文献引用多来源。发表日期、导入日期、检索日期分开保存；来源sheet也保存，不能只相信合并后的来源标签。公开题名/摘要信息与全文权利分开治理，先确认授权再决定存储/AI使用。首期先完成团队提供文献的可审计导入，再扩展自动采集，不等待所有外部来源连接器才展示真实领域内容。

### 10.4 代表方案与首期EDC

已核实的[官方注册研究202558](https://www.chictr.org.cn/showproj.html?proj=202558)提供认知方向、双盲、多中心、分组、量表/检查和CRF/EDC的产品参考；不是完整Protocol，也不能自动成为团队私有Study。项目200293暂未获得可核实正文，保留待核实引用。两项均不得把注册摘要直接转为已获批准、可采集的研究模板。

用户已明确“没有EDC，需建设数据采集”。首期增加以下需求：

| 编号 | EDC行为 | 必须验证 |
| --- | --- | --- |
| EDC-01 | 每个Study/中心管理受试者编码、筛选/入组状态及知情同意记录 | 编码与身份映射受控，不能由Hub公开读取 |
| EDC-02 | 按批准Protocol配置访视计划、窗口和CRF表单版本 | 团队确认配置后使用；变更不改写已有采集版本 |
| EDC-03 | 采集数值/日期/枚举/文本/附件，必填/范围/条件校验，草稿与正式提交 | 区分未测/未知/不适用/缺失与0；并发保存不覆盖 |
| EDC-04 | 数据疑问分配→回复→复核→关闭，保留原值/新值与改动原因 | 采集者不能删除审计或静默关闭所有疑问 |
| EDC-05 | 研究者审阅/签署，表单/访视/研究按政策锁定；受权解锁 | 变更后旧签署失效需重审；锁定后拒绝普通编辑 |
| EDC-06 | 量表原始项目/分数、版本与时点，检查结果及受控附件 | 算分依授权量表与确认规则；AI不填造结果 |
| EDC-07 | 不良事件记录、随访与处理状态；流程由方案确认 | 不以普通任务完成替代安全事件跟踪 |
| EDC-08 | 数据字典、受权导出、数据库快照、分析版本和服务端审计 | 标识/范围限制，数据可复查；用户身份与操作时间可追溯 |
| EDC-09 | 多中心及盲态角色限制，必要随机分配/揭盲记录 | 评价者/统计人员按方案隐藏分组；角色、导出、AI不能侧漏盲态 |

独立随机化服务、分层/区组算法、紧急揭盲和全套通用表单设计器不是已确认的无限范围；先确认首个Study需求。若方案要求这些能力，完成对应配置与验收后才能激活该研究；不能用任意前端随机数替代正式分配。首期目标是一个可复用、版本化的采集引擎与经确认的研究模板，不是一套无边界的EDC产品。

研究计划必须由完整Protocol、访视表、CRF样表和实际团队流程确定；没有明确时间点时不生成采集日程。当前S09演示访视不是正式EDC，仍需后端存储、授权、验证与审计。

### 10.5 研究内容与角色责任

教授可直接提供申报书的研究目标、研究内容、关键科学问题和技术路线；团队协助整理成“领域方向→项目→子课题/任务→Study/实验工作包→产出”。临床研究问题在Project内用PICO及必要时间维度整理；机制性问题保留适用的研究对象/假设/方法，不强制改为临床PICO。

建议流程为“立项/意图→设计与必要伦理/机构治理→注册与中心启动→执行/采集→数据清理与锁定→分析→论文/成果与资产发布”。这只是产品映射模板，尚未取得团队实际操作流程。

| 首期角色 | 责任 | 范围 |
| --- | --- | --- |
| Hub负责人 | 管理全部领域/活动/课题与研究数据，可自行研究和采集 | 本Hub；含PI和采集能力 |
| PI | 方案、成员、研究执行、数据审阅/锁定/解锁及产出 | 其Study，所有操作留痕 |
| 采集人员 | 访视/CRF录入、提交与更正、疑问回复 | 授权Study/中心；保留前后值和历史版本，锁定后须PI解锁 |

评价、质控、统计和发布作为任务或权限动作，不另设首期业务角色。数据更正生成新revision，PI审阅绑定revision，更正后新版本重新进入待审阅；历史数据和审阅记录保留。
