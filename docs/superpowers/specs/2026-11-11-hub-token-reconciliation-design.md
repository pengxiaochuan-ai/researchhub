# Hub Token 最小结算与租户内对账设计

日期：2026-11-11。状态：用户已确认本实施设计及第7节局部UI；已进入本机实现与验收，交付事实以[本轮记录](../../testing/hub-token-accounting-2026-11-11.md)为准，不代表生产发布或付费模型效果验收。

## 1. 目的与批准边界

解决“模型已消费、回答校验失败后长期占满预留”的新增问题，让管理员在Hub处理本租户待对账；不重建计费平台。历史15笔结算已经完成，不重复执行；原第12笔未知用量维持原样，不能因本规格批准而自动释放。

用户已批准：最小计费闭环修补与验收，以及“Hub租户管理员处理本租户待对账”。保留核验依据、真实操作者、审计、原额度和隔离。当前目录主实施串行，独立总评审；仅专用合成环境，不接临床库、不影响旧服务。不调用付费模型、不查供应商后台或远端配置，不充值、不增额，不操作云或发布。

### 现行规则校正

2026-11-05用户已经取消开发5/10元、累计任务/请求数、临时报价过期门禁，统一业务Token规则，见[现行规格](../../product/business-ai-quota-2026-11-05.md)。本轮此前“旧5元账本未覆盖新调用就是缺陷”的判断不成立。旧金额账本仅历史保留，不恢复为运行门禁；不将其剩余金额视作现行可用预算。

Token额度、实际Token用量、人民币成本估算、供应商现金账单是不同口径；本片只交付前两者的闭环与明确标识，不声称完成供应商现金账单核对。成本估算保留原值及来源，不用新价格重算历史。

## 2. 已核对的实现与问题

- 旧`SessionsService`成功提交在原事务内保存Message/UsageRecord和结算预留；继续复用，不额外记一次账。
- `requiresProviderReconciliation`对未知异常或任意partialUsage均为true，因此已知消费但交付被拒的任务也会保留整笔预留。这是现行保护策略，不能简单改成“partialUsage存在就自动结算”。
- 本机`local-knowledge-ai.mjs`的真实模型HTTP出口已限定官方地址并记录trace，通用/文献/OpenCode合成分支也必须逐一核对实际出口，不以一个适配器的单测替代覆盖。
- 原`BillingService.tokenQuotaReconciliations/resolveTokenQuotaReconciliation`只允许platform_admin；旧Web已有平台对账界面，但Hub未装配对应业务页。不能冒用平台身份调用原接口或全局放宽旧Controller。
- 现有`TokenQuotaReservation.reconciliationUsageRecordId`为唯一关联；`UsageRecord`、`AuditLog`及账号/租户表足以承载本片，首选不增加表或DDL。若真实PG权限或持久回执无法满足以下原子性，先停下说明最小差异，不临时使用owner旁路。

## 3. 方案取舍

采用Hub独立适配：原预留/正常结算继续原服务；Hub增加调用完整性回执、异常结算和租户内管理接口。自动结算只处理启用后带完整新回执的Hub任务，不批量处理旧记录。

不选全局修改旧Sessions/Billing的角色与异常规则：会影响旧服务、扩大共享底座。也不选租户管理员伪装平台管理员、在前端过滤跨租户结果、另建一套额度/金额账本：无法保证服务端隔离或账本单一。

这是在“旧权限不变、只增强Hub”约束下的最小推荐实现方向；独立适配不等于复制整个BillingService，确定性规则及正常服务调用继续复用。

## 4. 统一结算规则

| 真实情况 | Token处理 | 业务结果 |
| --- | --- | --- |
| 请求前拒绝、确定未发模型 | 原路径释放预留 | 明确失败，不编造用量 |
| 正常成功交付 | 原事务一次记实际用量并结算 | 展示真实结果 |
| 所有调用已完成且用量完整，但JSON/来源/业务检查失败 | Hub原子记实际用量、结算预留及留审计 | 任务仍失败，不补造答案、不重试 |
| 任意一次调用未知/缺用量/回执不完整 | 保留待对账及已知部分 | 明确未交付，等待核验 |
| 同一提交重放 | 同键同内容返回原回执；内容不同409 | 不重复扣费或释放 |

“有一份HTTP200或partialUsage”不是完整性证明。完整新回执需覆盖本任务全部真实HTTP尝试：服务端attemptId、实际任务/会话/预留/租户/账号绑定、发起/结束状态、模型、输入/输出/总Token、调用数量与receipt版本。计数与金额均确定性计算，LLM不参与。

完整性条件：任务执行已结束、没有在途/未知尝试、每个已发尝试都有可信完整用量、非负安全整数且输入＋输出＝总数、归属全部一致、尝试未重复计入，且与原用量累计可核对。混用模型保留byModel，不把某一模型用量当全部。不完整或不一致只能待对账，不能选择一个较小值结算。

### 持久回执与中断保留的具体落点

首选使用原AuditLog追加`hub.token.attempt.started/completed/unknown`及`hub.token.execution.sealed`事件，meta固定schema=`rh-token-attempt.v1`；绑定tenantId/accountId/reservationId/sessionId/jobId/原claim执行令牌、attemptId、顺序号和模型，结束事件再附可信用量/HTTP状态。不能仅用进程内数组或本地trace。不存提示词、回答正文或凭证于对账投影。

开始事件须与预留保护同事务提交后才发HTTP：先取得共同授权锁、旧reserve同名`aisci-token-quota:<tenantId>`额度锁，再按本租户及本人精确目标锁定active预留；锁内按数据库当前时间重验原expiresAt尚未到期，将该笔新Hub预留的expiresAt固定为`9999-12-31T00:00:00.000Z`（持久保留哨兵，不是可退款倒计时），同时登记开始事件及原到期值。不改变status=active，故旧成功CAS仍可用，原额度快照也持续计入占用。保护事务不调用原reserve的第二事务，避免同锁自等待。共同额度锁必需：仅行锁不能阻止另一reserve在原到期后通过MVCC旧快照误认为容量已释放。

原reserve仍按自己的租户quota锁原子预留；无已发attempt的预留继续原15分钟机制。保护事务失败则禁止发模型；已开始后进程崩溃也不会因15分钟到期漏占。此哨兵仅新Hub明确登记的预留，不回填历史或改旧系统策略。

结束/未知事件按attemptId锁与绑定指纹防重：重复同内容回读，异内容冲突且保守未知。所有实际HTTP尝试均登记，包括OpenCode分支、重试与失败；不能用一次SDK调用代替多次HTTP。无法受控记录的出口在发出前拒绝，B01不能证明覆盖就停线。

封口只发生在Hub会话执行包装层确认原Orchestrator及其业务校验已退出后，或Sessions异常结算回调中；Provider返回自身不算整轮完成。封口禁止该执行令牌新增attempt，成功/失败均封存实际attempt集合与指纹。正常成功仍等原发布事务完成；自动异常结算只能由原Sessions catch路径在业务失败已发生后触发，不能从Provider提前处理正常成功。

写结束事件失败、缺用量、HTTP500、网络/协议错误均保持未知并拒绝交付，不当零消费；开始记录和持久预留继续存在。已中断但仍active的保护记录可在本租户管理员核对中处理：锁内验证原job与claim，只有原claim确已失效、旧执行不能合法发布，且不存在原成功UsageRecord，才允许CAS转待对账。仍在执行的任务只显示“执行中”，不得人工结清。不得启动全库历史扫描或自动重放任务。

## 5. 租户内授权与API

所有请求通过Hub现有会话及同源JSON校验。服务端当前账号active、租户active、authVersion一致、role=tenant_admin且isTenantAdmin=true；不信任JWT孤立标记、邮箱、前端隐藏。读写均绑定部署允许的当前租户。普通科研人员仅可读本人额度，不得读/处理他人待对账。

拟新增Hub专属契约（最终路径细节可由实现者在本范围内定稿）：

- `GET /api/hub-billing/me`：本人业务Token分配/实际已用/在途/待对账/可用，读取不扣费、不续旧测试授权。
- `GET /api/hub-billing/reconciliations?page=N`：仅本租户、固定每页20；待处理/已处理切换，返回账号、发生时间、占用/已知用量、可核验状态及处理结果，不返回原文、密钥或跨租户信息。
- `GET /api/hub-billing/reconciliations/:id`：本租户详情、实际调用证据概要与历史处理回执。
- `POST /api/hub-billing/reconciliations/:id/resolve`：`requestKey`、服务端快照指纹、`action`、核验依据和必要的逐调用用量。tenantId/accountId/角色等不可由请求体指定。

`settle`只接受可核验的完整用量；本片管理员选定既有具名服务端证据集合，服务器生成只读用量，不开放任意填写Token后即视为核验的入口。`release`只接受服务端能证明从未发出的记录；缺失任何attempt开始事件本身不是未发出证明，不能用于清空旧记录。失败、过期或管理员身份均不是零费用依据，已知存在消费不得整笔释放。

本片真正可结清的是：完整可信回执已齐备，但自动结算未提交成功的记录，以及明确完整生命周期内未发出的记录。真实未知（网络超时、500无用量、崩溃缺回执）只展示待核实，不开放假释放主按钮；供应商账单/外部证据导入与验证另列后续，不在本片伪造。原第12笔不会因为管理员新页面出现就变成可结清。页面必须明确此能力边界，不能宣称所有历史未知已经闭环。

跨租户/不存在ID统一不可发现；同租户普通账号403，过期身份401，状态/证据/快照冲突409，缺项422。所有GET no-store，错误不泄漏数据库内部信息。

## 6. 原子性、幂等及兼容

1. Hub控制面允许复用原已有elevated事务机制，但必须在事务内先获取`wp01:tenant:<tenantId>`共同授权锁、重验当前账号/租户/authVersion和实际管理员，再对每条查询显式限制当前tenantId；这不是伪装平台角色或读取全平台后由前端过滤。原审计RLS只按项目可见，不能假设普通项目事务自然支持租户跨项目对账；不新增DB凭证/GRANT。普通`me`亦须当前身份及本人范围，不能复用管理员宽投影。
2. 新Hub统一锁顺序为共同授权锁→旧`aisci-token-quota:<tenantId>`额度锁→`hash(reservationId)`平台人工对账兼容锁→预留行锁；仅涉及的锁参与且不能逆序。旧正常成功/hold/release并不获取该reservation advisory锁，实际依赖status=active CAS；不得将新锁声称为全链既有保护。Hub自动结算只进入已失败的catch路径，人工只处理pending或已失效claim的中断记录；锁后重新读取真实状态，靠同一行CAS与旧成功/保留路径协调。正常成功若已提交，本片不得再记用量；若仍可能合法发布，人工拒绝处理。
3. 锁内重验待处理状态、全部调用证据、封口指纹和是否已有对应UsageRecord/结算审计。自动结算及管理员提交对同一目标互斥。
4. 同一事务写一条真实UsageRecord（或release无新消费）、修改预留及唯一关联、追加实际操作者/依据/回执。用原reservation状态CAS，任何失败全部回滚。核验过的真实消费即使超过原预留，也不能截断为预留量；原额度不足按既有业务规则禁新发，不补额度。
5. 正常成功链不重复记账。结果未交付不得追加伪助手消息或改成completed；异常后结算失败需明确标待核对，不能被错误回退掩盖。
6. 幂等键与规范化内容指纹存既有审计/回执；同键同目标同内容回读原结果，同键异内容409。结算成功但HTTP丢失时，刷新/原键重试可恢复，不新建目标。新兼容锁及行状态保护覆盖两个不同请求键竞争，不声称旧所有方法已统一advisory锁。
7. 旧平台管理员入口、旧服务源码/配置、历史用量/审计、原Grant和开发金额账本不改。新本租户对账审计记录Hub管理员原账号，不写平台管理员身份。B01须实证上述持久保护、受控事务及旧成功CAS可兼容；若失败，不承诺无需旧源码/DDL，先提交最小差异确认。

## 7. 已确认的最小UI

仅G02现有“系统配置”上下文中的“AI用量与对账”叶子；不增加一级导航，不改G02总览、团队/来源审核或其他页面。原科研人员页不新增运营表单；本人Token状态沿原业务提示展示。

管理员路径：进入→看到本租户待处理列表→点“核对”→站内弹窗查看账号/任务、占用和可信用量→明确一次“确认结算”。服务器完整回执可直接显示，不要求抄Token/模型/技术ID；无法核实的明确“待核实”，不提供假装安全的释放主按钮。具有零计费证据时才提供释放动作，影响说明就地显示，不连续二次确认。

成功后回读并更新列表/余额、关闭弹窗、恢复原查询/分页/焦点；失败/409保留输入并给出刷新核对入口。丢响应原键恢复，未知时不自动重发。Esc/取消/Tab约束、身份变化立即清私有内容与迟到请求；网络错误不误退出。操作14/22，关键错误不缩略，窄屏可操作，内部哈希/版本不成为必填技术操作。

现有G02原无此叶子，不能把新增交互冒称原布局不变。用户已在本聊天确认后实施；其余G02总览、团队/来源审核和全局导航布局不改。

### 实施定稿

- 成功结算同时比较完整回执与原累计的输入、输出、总数、调用次数、各模型Token/calls及主模型；不比较或重算成本估算。发现不一致，原发布事务拒绝，catch另在同一持久事务追加`hub.token.execution.inconsistent`并封口；自动及人工入口均保留待核实，不能用失败路径绕过。
- 保护回调明确失败且此前没有发出的尝试，保留原零消费释放；保护回调完成后COMMIT确认丢失则保守保留。不得混淆明确回滚与未知提交。
- 未确认的管理提交可关闭弹窗，不表示撤销结算。原记录ID/请求键/指纹按当前身份存会话恢复记录，不含凭证或正文；刷新后显式恢复、原键核对，无自动重试。浏览器存储不可写时本次结算尚不提交，给出可恢复错误。
- 详情显示任务说明，调用依据按需展开，已核验部分不冒充完整用量；已处理记录显示处理人、时间和实际消费。不让用户填写内部标识或Token数。

## 8. 小步实施与验收门槛

在B01证实无需新增Schema/旧源码适配的前提下，预计2个工作日＋半天缓冲，不包含等待用户评审、供应商用量获取或正式部署；否则先停线复估，不扩大成支付/套餐项目。

1. **B01（2h）**：冻结当前旧源码/角色/Grant/原15笔及未知第12笔、旧费用账本指纹；核对专用库/RLS、真实模型出口与事务锁。权限不足或完整持久回执无法满足时停止，不绕过。
2. **B02（3h）**：先写反例，完成Hub调用完整性/持久回执与异常归类；覆盖单次、多次、混模型、缺用量、500、重试、进程中断及到期，不发真实模型。
3. **B03（3h）**：先写真实PG回滚测试，再实现自动结算/未知保留和原子幂等；强制中途异常/不同键竞争/丢响应，不改历史。
4. **B04（3h）**：租户管理员列表/详情/处理接口；真账号/authVersion/撤权及跨租户测试，普通科研人员只读本人额度。
5. **B05（3h）**：批准第7节后实现最小叶子与原位弹窗，组件/受控浏览器失败恢复；不改全局布局。
6. **B06（2h＋4h缓冲）**：独立代码总评审、构建、两角色真实Chrome/截图录屏、真PG回读与产品文档/Notion；零模型网络请求。

测试对象优先在真实PG事务内新建后回滚，回滚不冒称持久功能验收。需持久化时仅本轮具名合成租户/账号/任务/预留/用量测试对象，明确synthetic标识；不修改已有账号额度或拿历史第12笔做“释放成功”样例。新测试对象不能进入原体验账号可消费额度或普通公开列表。

必测：完整已知失败按实记一次；成功原路径只记一次；未发出释放；任意未知/回执失败/500/中断不免费释放；过期不漏占，特别是持久保护事务尚未提交时另一reserve跨过旧到期时点的真实PG竞争反例；并发与不同键竞争只结一次；事务故障全回滚；同键丢响应恢复；权限撤销和跨租户拒绝；成本估算不冒充供应商现金账；所有当前AI分支均走业务Token预留及结算，无恢复旧开发门槛。

交付四层分别记录：代码测试、本机装配、真实HTTP/数据库效果、管理员完整操作体验。零付费替身能验证记账与控制面，不能冒称新真实模型用量验收；后续真实模型验收若需要新增调用另确认。本机通过不等于生产启用或供应商未知旧账已查清。
