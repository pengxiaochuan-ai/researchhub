# 邀请异常批量读取评估

日期：2026-11-16。状态：**评估完成／推荐方案待批准实施**。当前请求仅评估减少29个邀请读取请求；未新增运行接口、修改页面／旧系统／业务权限或执行发布。

## 结论

建议新增一个仅供治理总览使用的批量只读入口，**按最多10个Study一批、复用单个邀请读取事务，保留逐Study当前授权**。当前29个Study预计由“1次发现＋29次读取”变为约3个批量请求；以其余请求不变估算，整页API约36→9。异常或单Study多页时继续游标读取，3不是固定上限。

先复用现有邀请读取／状态计算和授权路径，不做共享底座改造、不建表／加索引／增加GRANT、不修改S11邀请、重发、撤销或接受流程。不要只在服务器把29次独立调用串起来；那样主要事务成本还在。

本机服务内对照有收益，**尚无新接口的真实HTTP或整页after样本，不能承诺整页262ms或已降至3秒**。实施工期建议1.5～2个工作日；目标为同规模合成环境完整列表中位≤3秒，未达即如实报告，不用请求数量代替体验验收。

### 现有执行路径

`loadInvitationExceptions` → `GET governance-users/studies` → 最多3并发`GET member-invitations` → `createInvitationRouter` → `createMemberInvitations.list`。

- 静态target命中2个Study；其余27个先`resolveTarget`单开事务验证group／project，再开邀请list事务。故业务仓储56次事务，不是29次；另有每个HTTP请求的会话校验事务和Study发现，未包含在56中。
- 每次仓储事务获取同一租户授权互斥锁、检查租户；每个Study再检查当前账号／authVersion、真实group／project、成员角色与管理权限并获取原项目锁。提高浏览器并发不能消除这些步骤的争用。
- 邀请list会分页读取所有状态，再由前端筛异常；现阶段绝大多数请求是空读。
- 表已有`research_member_invitation_scope_idx`；实际元数据确认RLS开启且FORCE，aisci_app已有SELECT。未发现需要新索引／表／数据库授权的依据。

## 方案比较与取舍

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 继续增加前端并发 | 改动少 | 仍29GET、56事务，增加租户锁竞争 | 不推荐 |
| 单HTTP包29个旧独立事务调用 | 浏览器请求少 | 后端事务／锁往返基本保留，收益不足以确定 | 不推荐作为交付 |
| 小批量请求＋事务复用＋原授权读取 | 减少HTTP与事务，复用最多 | 需新只读契约、游标和真实异常验收 | **推荐首步** |
| 新建通用聚合表／缓存／全租户SQL改写 | 理论吞吐高 | 需额外失效、权限与迁移设计，当前数据规模无依据 | 延后 |

本页邀请读取有原事务保护；Study发现与邀请读取不是同一快照，各页也不是同一全局快照。先结束发现、再逐Study当前授权与现有前端分开请求的语义一致；没有把前一次发现当成后一次授权结果。本轮选择保留两种既有仓储角色与锁边界，避免为只读性能新建跨仓储原子协议。

每页重新发现当前合法Study范围会重复一部分目录成本；原型没有计入这部分，也没有模拟HTTP会话守卫，因此不能按88ms差值或29→3直接给整页收益承诺。实施后必须计入3页范围发现、锁持有与守卫的总成本；若抵消收益，应继续在本接口内分析，不自动扩改通用目录／会话／锁。

首步仍复用原分页和状态计算；不急于把全部授权改写成一个新SQL。先移除明确的HTTP／事务重复；大量历史邀请时，由扫描游标限制每页工作量，不能仅过滤后空集合就误判读完。

## 推荐最小契约（草案，非已实现）

`GET /api/member-invitations/exceptions?cursor=...`

- 服务端发现当前可管理的Study，拒绝客户端指定tenant／actor／任意scope清单。复用真实会话守卫及原本地来源规则。
- 每页最多10个Study、扫描最多200条原邀请、交付最多50条异常；到任一边界返回有效续读游标，不截断后宣称完成。单Study超过50原记录时同样可续读。
- 返回`items`、`nextCursor`及机器可读的`coverage.complete`；有nextCursor即未完整。items只有原异常字段及精确group／project／Study名称，禁止泄露tokenHash、requestHash、邮件正文、原始响应或新增账号信息。
- 游标含版本、tenant／actor／authVersion绑定、稳定Study排序锚点、当前Study邀请分页锚点、范围摘要，使用已有服务端密钥进行目的隔离签名；不建缓存表、不暴露密钥。每页重新发现当前合法范围并校验摘要，观察到范围变更即返回明确错误；摘要只表示该次发现的集合，不是邀请状态版本或全局即时权限快照。
- 每页先执行并结束现有Study发现（原app角色，official→tenant），释放其事务／锁后，再开本批邀请读取（原WP02角色，tenant→project）；是两个顺序执行的兄弟事务，禁止在持有WP02租户锁时调用自开事务的发现服务，也禁止后拿official。邀请事务内显式绑定本批原list调用，逐Study原身份、真实父对象、角色及项目锁检查保留；不换数据库角色、不新增高权旁路、不因邮箱判断管理员。当前29Study预计3个邀请事务＋3个发现事务，另含HTTP鉴权；原型表中的3仅邀请侧，尚未测这6个事务的端到端总成本。
- 异常状态仍为failed／unknown／expired，accepted／revoked优先排除；按每次实际读取时的服务端当前时间计算过期，不引入时光冻结的新业务规则。无异常是合法成功空集合；未读完不是零条。
- 会话失效401、当前目标失权403、游标/范围变化400或409、读取失败503；任一页失败时整项邀请分类明确失败／拒绝，不把半个结果当成功。保留现有其它类别先显示、20秒总期限与身份切换取消；不自动退回29请求或自动重试。
- 前端只替换治理邀请adapter，完整遍历后才发布邀请异常集合；原关注折叠、排序、S11精确定位和返回位置不变。无新增按钮、筛选、提醒或开发文案。

### 对三端与数据库的影响

- 管理员：同样列表／入口／处理能力，加载更少请求。
- 科研人员：仅本人已有成员管理权限的Study，当前owner为0仍正确显示空集合；不因此新增邀请授权。
- 后端：一个专用聚合读路由、请求内事务绑定、严格游标／返回校验；原单Study读写接口保留。
- 数据库：复用原邀请表、索引、RLS和既有授权锁；暂不迁移／加GRANT。Study发现保持原app/RLS路径，邀请读取保持原WP02路径，禁止为了复用事务换成同一高权角色；实施仍需验证两种角色及集合等价。新库权限与生产适配另验，不能以本机权限证明正式部署已可用。
