# 团队、成员与待审机构同页人工核实：最小实施规格

日期：2026-11-06。业务方向、规格及计划已批准；代码、本机启用和合成真实请求/浏览器技术交接完成。真实资料专业验收及本机事实额度调整待用户，不是生产发布。[证据与限制](../testing/team-admin-review-2026-11-06.md)。

## 目标与非目标

管理员在现有团队维护页一次核实团队、成员、所选待审机构并明确审核。本人核实是诚实的目录依据，不伪装论文或网站。保持列表、三段表单、Shell及审核主动作；不扩展共享底座、旧系统、权限、Study授权、L2/L3、AI模型或科学数值能力。仅专用合成环境；不代用户批准真实资料。

## 已选方案及技术选择

用户已选择允许管理员本人核实，并将团队和待审机构同页审核；仅保留外部资料路径无法满足此目标，故作为可选旧路径继续保留。推荐复用目录entity.team_draft的受控JSON存储核实记录，并用新admin_verification引用类型接入目录事实的既有provenance，不另建来源库、资料导入批次或旧系统表。

新建独立资料库会增加Schema/授权/导入审核环节，与本次减负目标不符；直接删除来源校验则无法追溯。选用上述既有目录内的受控记录方案。若实现发现必须增加数据库权限或突破现有JSON/数量保护，停下说明，不以direct数据库连接绕过应用权限。

## 页面路径与局部交互

- 进入、查找、选择团队及三个资料分区顺序不变。
- 仅在“3.资料依据”分区承载“管理员本人核实／关联已审核资料”方式。建议本页默认本人核实，并明确显示当前方式；这是技术/交互建议，不改变其他页面或旧API省略字段时的原来源模式。
- 本人核实模式不要求再检索外部文献、逐条勾7个关系或额外输入一份理由；复用原页必填审核理由作为核实说明。
- 同区显示去重后的待审机构名称、当前状态和本次将审核的范围；机构现有完整概况可按需展开核对。不能把用户未看见、不可访问的机构内容静默纳入审核。
- 原“保存草稿”仍可资料未全；点击原“审核通过并展示”才产生核实与决定。常规一次提交；新增公开曝光沿用已有简短确认，并明确包含待审机构，不重复整份团队表单。
- 反馈明确区分“草稿已保存”“本次未提交审核：仍需补齐…”和“已审核展示”；阻断时保留资料与理由，不让按钮表现为无响应。
- 修复高级机构入口将已填理由误作未保存资料的问题：离页仍保护理由；其他目录维护只阻断真实未保存资料、未知提交或忙碌操作，不因仅有理由而要求反复保存。
- 审核准备逐项比较联合机构完整profile与界面已读快照；不同则刷新原位核对内容、保留资料/理由并停止本次提交。不能仅因机构ID未变而沿用旧简介，409对照保留输入后也同样检查。
- 字号14/22、44px控件、原配色/间距/三段表单保留；1440/1366/1920/390/320及原生200%实测，不靠缩字或裁切精简。

## 数据与可追溯性（不新增表、列或授权）

1. 私有草稿data仅增加可选verificationMethod（administrator/sources）；省略时后端保持旧sources语义。本人核实不是保存时自动完成的布尔认证。
2. 仅在明确审核的原事务中生成核实记录，保存在team_draft.verifications，包含服务端ID、租户/Hub/团队、草稿版本、实际确认人及显示名、服务端时间、审核/核实理由、audience、核实事实摘要与claimDigests。
3. claimDigest绑定具体entityId、assertionKey、事实kind、relatedEntityId、规范化payload及实际新revision；不能把一次核实借给另一团队/关系/修订。新建机构/人员先分配实际ID，再生成绑定。
4. admin_verification引用沿用来源引用结构：sourceId=团队ID，versionId=核实记录ID，rowId=null，sourceHash=完整核实记录的规范哈希，locator为人工核实描述，fieldNames仅接受专用目录范围。记录hash由不可修改的assertion.provenance承诺；不靠可改草稿自身的hash自证。
5. 保存、重读、联合审核均保留旧verifications；前端data不允许提交确认人、时间、记录内容或伪造ID。任何错误、重试、未知结果均按原requestKey恢复，不另建核实记录。原100操作/250KB等上限不提高。
6. 原来源类型的查找/锁定/版本语义不变。人工记录读取验证租户/Hub/来源团队、记录哈希、audience及事实claim绑定；提交前锁定对应目录行并重验，不调用仅接受外部来源的旧source-lock函数，也不新增授权。
7. 人工依据仅支持目录概况、任职和团队成员事实，不可成为论文/指南、成果work、统计coverage、L2/L3或Study权限依据。通用append、读取投影与decide都要核对claim，不能只在页面入口校验。
8. 管理员能看完整核实追踪；公共T01/T02只诚实展示“管理员人工核实”及必要时间/范围，不泄露登录邮箱、私有理由或内部核实快照，不伪造外部链接。

核实记录是历史依据，原团队以后保存新草稿、收窄展示或软归档，不自动抹掉已核实的共用机构依据；记录仍保留在原目录行，仅按租户/Hub和记录哈希读取。历史核实人的离职/停用不改写其当时的核实记录；新提交始终检查当前管理员身份。对错误事实的撤回继续使用对应assertion的原决定链，不以撤回团队事实暗中撤回独立共用机构。本期不新增全局批量撤回核实记录能力。

实现边界：`resolveDirectorySource(tx,scope,ref,{fact}={})`只增可选上下文；人工来源缺少具体事实绑定时不能作为可提交依据。仓库缓存对人工类型须包含claimDigest，不能按同一ref缓存第一项匹配后把其他事实误判有效。核实记录读取与公共输出分开，不让内部claim列表随公开provenance泄露。

`teamSeed`不将admin_verification回灌可编辑data.evidence；后者继续只承载原三类外部引用。人工核实记录由workspace单独提供只读追踪。人工预检使用服务端可信的待核实提案，不以缺fact的人工来源查找冒充提交校验；实际读取、通用append和decide均按具体fact与revision校验。

原sources模式保持原锁定语义。administrator模式区分本次新增人工依据（incoming）、被该人工事实替代的旧依据（outgoing）与继续使用的父对象/关系依据（retained）：outgoing纳入planHash/CAS但不作为新独立人工事实的有效来源前提，不修改其撤回状态；retained仍须锁定并重验。未采用的data.evidence不构成人工审核前提，也不因留在草稿中被批准。已审但依据失效的共用机构仍阻断，不借此覆盖。

预检仅生成确定性的待核实提案及planHash；确认时间、随机记录ID和最终完整记录哈希在实际提交、分配真实对象ID后生成。不可为稳定预检而让前端传确认时间，或以仅包含草稿摘要的hash冒充整份核实记录hash。最终保存必须使用带新增verifications的同一份草稿状态，不能拿旧d覆盖刚写入的核实记录。

## 机构和成员联合审核规则

- 在当前租户与Hub、直接由本草稿引用的机构中去重，只联合处理从未审核/待审的概况，不遍历批准整个机构目录。“从未审核”须查询概况事实的历史审核，不能仅看最新head无决定；历史曾批准、拒绝或撤回后另起待审修订的机构，保守阻断并沿用原独立维护路径，不自动恢复或扩围。
- 已对本次audience有效审核的共用机构不重复写决定，不改其资料或原范围。
- 待审共用机构核实的是已读当前概况；名称/类型/完整内容与预检快照不符即409，不覆盖机构档案。可新增一版内容相同、依据为本人核实的事实再审核，保留原待审历史。
- 已拒绝/撤回的机构、仅租户已批准而本次试图扩大为公开等情形明确阻断，不将其伪装为“待审”自动恢复/扩围。
- 新成员按本次本人核实创建目录档案及任职/团队角色，不创建账号、发送邀请或授予Study权限。已选已有研究者的共用档案仍不被此表单覆盖；其当前资料须可用于本次范围。
- 预检planHash同时绑定草稿版本、全部真实父对象/机构快照、来源状态、核实方式、当前管理员及本次范围；最终仍两次核对来源/状态、当前授权和CAS。
- 同一事务完成必要对象/人工核实/事实/审核决定/草稿/审计/回执；任一步失败全回滚，不留下“机构通过但团队失败”的半截。成功后原数据从后端读回。
- 未修改、已对本次范围有效审核的事实保留原依据；本人核实只覆盖本次需要审核的变更，不自动替换全部旧外部依据。若业务内容/关系/范围均无变化且已有依据有效，反馈“没有待审核变更”，不新建核实记录或追加审核。
