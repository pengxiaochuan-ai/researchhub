# G02待处理事项加载性能

2026-11-16用户反馈“代理处理事项list加载慢”；按当前管理治理总览“待处理事项”定位，保持原布局／排序／权限／分页及失败语义，仅本机专用合成环境、只读浏览器，无模型／持久业务写／云；最后经已授权协调进行一次本机owned合并加载。

## 基线与最小方案

`before-1794801782183/result.json`三次真实Chrome：首次事项显示中位7104ms、队列完成6955ms、36个API请求；29个合法Study邀请GET串行，完成跨度中位5235ms。来源review-queue约1.2–1.3s已返回；方案审核遍历两页最终约6.9s返回。总览Promise.allSettled全部完成后才发布一次state，造成快类别跟随慢类别等待。不是仅凭代码猜测。

串行实施：
1. 先RED覆盖分类逐项状态、取消/迟到与错误不得伪零；邀请最多3并发、原scope/cursor/顺序、失败取消且不返回半个邀请集合。
2. 分类独立读取／发布，加载中明确标识；成功类别先显示，最终排序／去重不变。非第一页在加载完成前不显示错误的临时页码；翻页在所选类别读完前禁用。保留原区域，不新增控件／导航／CSS。
3. 邀请限3并发复用原权限API，仍完整读取所有页，不缓存授权结果、不减少检查、不提前报0。失败保留原403/503，取消未完成读。
4. 同一脚本三次真实Chrome前后对照；慢响应、读取失败、身份变化、分页返回和最终数据一致验证，截图录屏。若并发无收益或加重故障则回退该部分，保留已证实改善的首屏发布。
5. 单次独立总评，集中修补、回归／构建／文档与Notion同步；不扩共享底座或改旧服务。数字是本机合成实测，不代表生产SLA。

## 复测定位的同页后端瓶颈

首轮前端修补后首条事项中位1584ms，邀请跨度2929ms，但全部类别中位7289ms（首次冷样本13154ms，原件保留）。方案待审队列对每一条研究调用一次全目录读取；目录函数每次又扫描全部研究组，形成重复工作。只在本页方案队列引入请求内最多25条预取，复用完全相同的授权目录查询，并为每条保留精确原始游标；逐研究当前权限／feature／待审版本检查不变。公开目录返回不增加字段，不缓存账号权限，不建表／索引／通用聚合底座，不改写路径。保持原v1队列游标及25扫描上限，验证中途分页、无Study条目、权限撤回、微秒排序不丢不重；需要加载时仅协调本机owned服务。
