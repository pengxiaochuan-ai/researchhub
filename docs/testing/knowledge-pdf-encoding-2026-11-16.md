# 知识资料 PDF 乱码定位与最小修复边界

状态：用户批准的最小共享解析器修补已完成本机技术验证；非正式发布，也非 OCR 全文准确性签收。2026-11-16 用户指定 `docs/202307101606411075.pdf`。本轮不恢复资产问答或其他历史计划。

## 已验证事实

- 指定文件为 11 页公开团体标准，SHA256 `b9502dabb58c2b5113e4927592a13858a0310c332babad75d26b2b769cd654f2`，428586 bytes；首页图像题名为《真实世界针灸临床研究中仪器设备使用的记录数据规范》，标准号 T/CAAM 0010—2020。
- PyMuPDF 直接抽取首页得到 `犐犆犛１１．０２０`、标点序列及异常汉字。相关字体 ToUnicode 将字符代码映射到这些字，并非浏览器把 UTF-8 当成其他编码。另一份本地标准也呈现同类问题，但不得据此自动批量修复资料。
- 独立生成的正常中文 PDF，在同一解析代码和 Python 环境下标题、正文正常，未启用 OCR。
- 指定 PDF 首页有 238 个抽取字符，显著超过现行 OCR 触发下限 20。`app/kb-doc-parser/serve.py::_render_pdf_page` 因而信任错误文字层。部分其他页面同样有足量乱码。
- `pdf_literature_metadata` 再次从原 PDF 的字体文本层抽取题名、作者，正文即便改为 OCR 也不能据此假定标题已修复。`EpxService PDF Output` 是制作软件元信息，不是可信作者。
- 本机 Tesseract 首页 OCR 可恢复主要中英文内容；当前 2 倍图像样例仍漏掉题名中的“备”，另有标准号破折号/发布字样识别误差。因此仅证明视觉识别路径可用，不证明标题或全文科学准确，不可用替换字典静默补字。
- K01 文档 `contentMd` 为正文同源数据；富文本和 Markdown 共用它。应修正抽取源头，不能在两个视图分别猜编码或替换字符。初次定位阶段未实际操作 K01，不把当时的代码追踪称为浏览器复现；后续真实上传和视图验证见下文。

## 最小拟修复

1. 在 PDF 解析边界增加文本层质量与字体映射异常检查；逐页判定，保留正常文本 PDF 的现有路径。不仅检查 U+FFFD 或字数，也不能仅按“罕见汉字”批量判断正常专业文献为乱码。
2. 异常页面使用现有离线 OCR；标题和作者不能再读回该页坏文本层。题名须避开 ICS/CCS、团体标准标头、制作软件元信息，保留真实题名及必要人工核对。
3. 异常页 OCR 未产生可用内容、执行失败或超过限制时明确失败/缺页，不以原乱码或不完整正文冒充成功；保留原件供核对。不调用付费模型、不补造科学数值。
4. 补充正常中文、混合正常/异常页、异常标题、无文字/空白页、OCR 失败的回归；用具名新合成资料走上传→原件→抽取预览→富文本→Markdown→刷新→管理员只读核对，截图/录屏并独立总评。保持 K01 布局、权限和交互。

本机19503通过 `docs/test/evidence/2026-10-22-researchhub-synthetic-ai-trial/isolated-service.py` 直接复用 `app/kb-doc-parser/serve.py`。因此候选改动为旧项目共用解析器 `app/kb-doc-parser/serve.py` 及其 `test_serve.py`；不复制另一套解析内核，不修改受保护共享启动入口。

用户已批准这一必要共享源码修补；只在本机隔离解析进程/专用合成环境验证，不重启、发布或切换旧服务，不改数据库结构/权限。共享本机进程的重载需先协调窗口，不能抢占其他任务。

实施顺序：P01 用合成 PDF 写失败回归 → P02 逐页检查替代/私用/控制字符与实际使用的缺 Unicode 映射自定义嵌入字体，正常专业罕见汉字不单独触发 → P03 复用本地 OCR 并从可信识别正文提取低置信题名，不把软件署名当作者 → P04 测试与指定公开标准离线复验 → P05 协调本机环境采用修补，以具名新合成 PDF 进行浏览器双视图、刷新和管理员核对 → P06 一次独立总评与文档同步。真实空白页允许为空；存在异常文本或非空扫描画面却 OCR 无有效文字时明确失败。该启发式并非任意字体乱码识别或 OCR 准确率承诺。

现有资料与历史版本本轮只读，不清空或覆写乱码记录，不撤回/改变审核与检索状态。已有乱码资料修复需在解析修补通过后，精确确认文档和版本，再沿已有版本/CAS/重新审核流程处理；不得批量重解析、覆盖人工编辑或保留旧审核标志后直接入检索。
