# 团队保存409：编辑基准修补

## 验收问题与只读实核

用户点击“审核通过并展示”，在前置保存阶段返回DIRECTORY_VERSION_CONFLICT。该提交包含data/baseRevision，而非审核端点的planHash，因此失败发生在保存，不是已经审核失败或批准。

真实团队草稿仍为version1，保存时间2026-11-04T02:26:04.736Z。用户提交基准1841850f…正是服务器返回的历史草稿baseRevision；同次读取的currentRevision已经是329b783e…。页面错误使用历史基准，导致即使刚读取当前服务器状态也必然409。

## 最小实施方案

只改前端同一团队页的写入衔接：保存使用本次已读取workspace.currentRevision（旧响应无该字段时仍用baseRevision），不在提交前偷读新基准、不在409后自动重发。干净但目录基准过期的旧草稿进入审核时，也先用当前已读基准保存→重读→预览；确认批准仍是原独立命令。

保持后端CAS、来源版本、权限、审核和事务不变，不改API/数据库/页面布局或旧系统。读取之后真正发生的草稿/目录变化仍409，继续走原明确对照恢复。空白成员与缺资料依据可以保存为草稿，但预览必须列缺项且禁止批准，不将其错误修补为自动审核成功。

## 计划与边界

先RED测试→两处提交统一基准→真实回滚PG验证保存/来源/并发/人工审核→原合成团队真实Chrome回归与一次独立总评审。只用专用合成环境，真实团队及用户表单不自动保存/批准，无付费调用、云、配置、旧服务或发布。
